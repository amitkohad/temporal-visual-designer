# ADR 0011: Persisted whole-project activation

Status: accepted for local backend activation of target-local releases.

Each organization/environment/project has one active pointer. An immutable operation record stores the whole release snapshot, executable checksum, interpreter version, destination configuration revision, prior release, actor and revision. A SQLite `BEGIN IMMEDIATE` transaction compares the expected revision and commits the operation receipt, pointer and success audit together. A single read joins the pointer to one complete snapshot. Independently requested starts may legitimately see different releases when activation happens between requests; each start resolves a consistent project snapshot.

Activation and rollback require fresh `package.activate` or `package.rollback` authorization before idempotency lookup. Identity uses the existing signed-token/project authorization adapter. Production business authors remain denied; production support can deploy. `run.start` is added for business authors in Dev/UAT and production support; `IdentityStartAuthorization` rechecks grants for every start. Current-state/audit reads require `run.read`. These are environment-scoped grants; finer project ACLs and HTTP endpoints remain future work. Synthetic signed-token tests are not live Entra acceptance.

Operation IDs are scoped by organization/environment/project. Retries of the same full request return the original receipt even after later activations, without resetting the pointer or requiring the previous destination readiness to remain unchanged. Changed content with the same operation ID conflicts. First activation expects revision zero. Rollback requires a previously successfully activated release in that same scope, then rechecks current configuration/activity/runtime readiness. Rollback changes future starts only and never reverses business effects.

The source must supply an immutable release already present in the target environment. Scope/project/release identity, project structure, exact artifact closure and both content/executable digests are verified. `ProofActivationReadiness` compiles all workflow graphs for `proof.v1`, checks exact catalog versions and nonwithdrawn state, requires an explicit worker-capability provider, and requires an explicit immutable destination-configuration validator. Activation does not invent business input to satisfy required fields: structural compilation omits the input instance schema, while original schemas remain stored and enforced at start. Referenced schemas remain rejected consistently with the proof compiler. No bundle code is imported or executed by activation.

Activation acquires source release and exact activity holds before committing its pointer. All successfully activated releases/artifacts remain conservatively retained across rollback and active executions. Holds use deterministic internal operation references. The source, catalog and activation databases are separate local providers: there is no cross-database atomic transaction. Failure or a losing concurrent activation can leave extra holds; cleanup is deliberately absent until run/reference lifetimes and recovery orchestration are defined. Failure acquiring holds leaves the pointer unchanged. Transient withdrawal/capability changes across providers are not a distributed atomic readiness guarantee; production coordination remains open.

Audit records include actor, scope/project, operation/action, release, verified checksum, prior release, timestamp and outcome. Successful receipt/pointer/audit are atomic; authorized rejected attempts record sanitized outcomes when storage is available. A checksum is absent when no valid release was obtained. Denials are handled at the identity boundary and cannot claim an authenticated actor in the activation log. Storage outages cannot guarantee a rejection audit write. Retries after a committed-but-lost response reconcile the original receipt. Local audit storage is not tamper evident.

`ActivatedReleaseResolver` is an internal trusted port consumed by the start services after authorization. It returns a workflow plus binding from the stored whole-project snapshot. New activation/configuration revisions cannot alter existing persisted start intents or Temporal plans. A real local Temporal test keeps runs from A and B waiting concurrently, rolls back to A, starts a third run, then completes and replays all three with their original bindings.

Portable project export/import, environment binding storage, actual worker capability discovery, evidence fields/uploads, Admin/Designer UI and production database migrations/HA are not implemented by this decision. Missing change evidence never blocks this backend activation path. Production tests seed target-local releases through trusted repositories solely to test authorization; that does not establish a secure package import path.

The end-to-end test also corrects ADR 0010's adapter implementation: SDK start handles expose the accepted run through `result_run_id`; `run_id` is unset on a newly started handle. The offline fixture now models both properties and real activation/start acceptance exercises the normal acknowledgement path.
