# ADR 0018: Durable one-shot task notifications

Status: accepted for bounded local notification persistence and delivery.

Human-task notifications use an explicit internal service over the existing scoped task database. A trusted caller with `task.create` authority schedules a single reminder or escalation notification using an aware due timestamp, a schedule ID and the current task revision. Scheduling snapshots the current unvoted recipients. Escalation is a notification kind; it does not change assignment, approval rules or workflow routing. Repeating reminders require separate schedules.

Schedules are immutable and scoped to their task. Exact schedule retries return the existing record, while a reused schedule ID with different inputs conflicts. Each task permits at most 1,000 schedules, including completed records. A new schedule increments the shared task revision; retrying the same schedule does not. The persisted occurrence has a stable notification ID and contains task identifiers, due time, kind and recipient IDs. It contains no form values, approval comments, tokens or workflow variables. Notification records do not change the existing completion outbox or expose form state.

An explicitly invoked worker calls `deliver_due` using an injected clock and a batch limit from 1 to 100. Pending records survive restart. Delivery failures increment attempts, retain a safe fixed error category and defer retries using a configurable fixed delay from 1 to 86,400 seconds. The service returns counts and exposes records and payload-free audit events for failure observation. There is no automatic scheduler, HTTP scheduling endpoint or background worker in this increment.

Before sending, delivery rechecks task state, eligible recipient IDs and remaining voters in the SQLite writer transaction. When their due records are processed, terminal tasks and stale recipient snapshots cancel their notification. Reassignment that preserves the same eligible IDs and remaining voters does not invalidate that snapshot. The sink callback runs inside that transaction so a decision cannot commit a terminal transition between eligibility checking and sending. This intentionally serializes task writes while delivery is active. Hosts must bound the callback timeout and must not reenter the task database from the callback. This local adapter makes no high-availability or throughput claim.

External delivery cannot be committed atomically with SQLite. A process failure or uncertain acknowledgement after the sink accepted a notification can cause another delivery attempt. Sinks must durably deduplicate the stable notification ID and acknowledge only after acceptance. The payload remains identical across retries. A subsequently cancelled record prevents further attempts; it cannot prove that an earlier uncertain attempt had no external effect or retract an accepted message. This is an at-least-once boundary, not a guarantee of exactly-once external effects.

Transport adapters, connector credentials, Azure hosting, automatic timers, live directory providers, browser configuration and Temporal human-task progression remain separate work. Existing Entra and task authorization boundaries continue to apply; no delivery callback can grant task permissions.
