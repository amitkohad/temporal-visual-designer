# ADR 0006: Authoritative form validation and preview

Status: accepted for the local backend increment.

Implement `FormService` behind a trusted `FormGateway` port. Each preview/submission freshly authorizes the scoped resource and loads its definition, values, revision and server-owned readable/editable fields. Submission accepts only a JSON patch and expected revision; callers cannot supply authorization context. Commit adapters must recheck authority and revision atomically. No task/start HTTP handler, live identity adapter or production form storage is supplied by this increment.

A preview is an immutable JSON-only view: ordered fields, labels, field schema strings, editable/required flags and readable visible values. Labels are plain data; React must render them as text. Top-level writeOnly fields omit values and strip defaults/enums/examples from preview schema metadata. Hidden or unreadable values do not participate in preview visibility or required hints, so those hints cannot disclose protected state. Business validation still sees the complete stored/merged values. UI visibility is never authorization.

A submission is a partial top-level patch: supplied values replace those fields; omitted fields retain server values. It cannot delete fields. Every supplied field must be readable, editable, visible in the resulting permitted view, and not readOnly or marked read_only in field_permissions. Even supplying an unchanged protected value is rejected. Unknown fields, duplicate JSON keys, nonfinite numbers, invalid Unicode, excessive bytes/depth and stale revisions fail before commit. Failed validation makes no persistence call.

Forms require a closed top-level object schema with explicit typed fields. JSON Schema 2020-12 validates full merged values and business rules, including native if/then/else and dependency conditions. Required hidden fields remain required when their business rule applies. Visibility rules are versioned `{schema_version: "0.1", field_id, when: <JSON Schema>}` declarations; validation rules use `{schema_version: "0.1", data_schema: <JSON Schema>}`. These reuse offline JSON Schema evaluation rather than introducing a general expression language. Required hints cover required/allOf/if/dependentRequired/dependentSchemas on permitted preview data; submission validation is authoritative.

The initial subset rejects remote/local schema references, user regex keywords, anyOf/oneOf, nested readOnly/writeOnly annotations, arbitrary layout keys and attachment policies. This avoids unsupported schema implication, nested permissions and regex backtracking. Supported native format checks use installed local validators. The form layout currently supplies field_order only. Attachments, dynamic read-only rules, general expressions, rich layout and browser accessibility remain later increments.

Project publication through AuthoringValidator checks each form definition and reports form-located issues. Existing pinned releases remain immutable. Baseline credential-key heuristics recognize versioned schema declarations and boolean field permissions as metadata; arbitrary embedded secrets/schema defaults still need stronger policy and are not covered by a DLP claim.

Isolated tests prove gateway contracts and business validation with fake authorization/storage. They do not establish deployed Entra access, production persistence, UI keyboard behavior, submission idempotency after response loss or bounded evaluation time for all adversarial JSON Schemas. These require later adapters and operational limits.
