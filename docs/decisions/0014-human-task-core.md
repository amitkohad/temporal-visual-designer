# ADR 0014: Durable approval core before portal integration

Status: accepted for the isolated approval backend; HTTP, live identity and runtime integration remain separate gates.

Human approvals belong to a separate backend module with explicit identity, assignment and runtime-completion ports. This increment implements the bounded `any_one` and `all_approvers` policies. It establishes durable approval semantics independently of browser screens, HTTP endpoints and Temporal transport adapters. Existing runtime feasibility tests do not establish acceptance of this module.

Task creation pins the organization/environment, workflow execution and node invocation, definition revision, approval policy and resolved eligible Entra object IDs. The invocation identity distinguishes repeated visits to the same workflow node. Creation is idempotent within that scope: the same invocation and exact request return the original task, while a conflicting request fails. User/group tuple order is part of request identity. An assignment resolver expands explicit Entra users/groups, deduplicates resulting users and rejects an empty set. Each supplied principal collection and the raw resolution result are bounded to 1,000 entries; resolution must produce a tuple of valid immutable IDs. The resolved assignment is an immutable snapshot. Later group membership changes do not silently rewrite a task or invalidate committed decisions.

Every public operation uses an injected trusted authorization port that freshly checks `task.create`, `task.read` or `task.respond` policy and returns the immutable actor ID. The service accepts a scope, not caller-supplied request-context permissions. The server checks the requested placement and task scope before returning task data or accepting a decision. A caller must remain authorized for the placement and belong to the pinned eligible set to act. Assignment snapshots provide stable approval membership; they do not grant access to a foreign environment or bypass revoked placement authorization. This increment does not add grants to existing roles. Live Entra membership and transport-level authentication remain adapter work.

Approval commands carry a command ID and expected task revision. Accepted commands and their canonical contents are durable. An exact retry returns its recorded outcome; reusing the command ID for a different command fails. New commands use compare-and-set revisions to prevent conflicting updates. A user can contribute at most one decision. `any_one` approves after one approval; `all_approvers` requires every distinct eligible user. A rejection terminates either policy. No decision can mutate a completed task.

SQLite transactions commit the decision, task revision, audit record, command receipt and terminal completion outbox together. Independent repository instances must serialize competing writes through the database, rather than relying on a Python process lock. A terminal task produces one stable completion identity. The outbound record contains the pinned task/execution identity and final result, not a newly evaluated approval policy.

Delivery is an explicit internal worker operation in this increment, not a publicly authorized API. It reads pending durable records and calls a completion sink using the stable completion identity. Acknowledgment is persisted only after the sink accepts the completion. A crash between acceptance and acknowledgment causes redelivery; therefore the sink must deduplicate by completion identity for the supported retry lifetime (the port requires permanent deduplication). This provides durable at-least-once delivery with an idempotent recipient, not an exactly-once distributed transaction. Sink failures leave the record retryable and cannot reverse an approval. Real Temporal signaling and workflow-side deduplication must be verified separately before connecting this module to execution.

Forms and submitted business payloads, attachments/scanning, timers/reminders, notifications, sequential stages, conditional routing, request-information actions, claim/release, delegation, reassignment, inbox queries/pagination, HTTP endpoints, live Entra adapters and actual Temporal completion delivery are deferred. The local launcher and proof interpreter do not gain human-task support implicitly from this module. Full feature tasks remain open until their original acceptance is satisfied; completed backend slices receive explicit subtask evidence.
