# ADR 0010: Journaled Temporal starts

Status: accepted for the local proof-runtime start adapter.

`AsyncStartService` shares preflight, authorization, canonical request identity and durable plan preparation with the synchronous start service. It awaits an explicit async dispatcher; no nested event loop or blocking bridge is used. Local SQLite and authorization/release ports remain synchronous. Production async persistence/provider adapters and load testing remain separate work.

`TemporalStartDispatcher` requires an SDK client, a private durable `SQLiteDispatchJournal`, trusted organization/environment scope and task queue. It supports only `proof.v1` and server-generated `nf-<32 lowercase hex>` execution IDs. The journal binds each execution to its full plan digest and destination (client target host, namespace, queue and scope). Destination changes fail with a conflict. Only the winning persisted claim issues a start RPC, with `REJECT_DUPLICATE` for closed IDs and `FAIL` for running-ID conflicts. RPCs have a configurable positive timeout, default ten seconds.

The journal is permanent, even after Temporal history retention expires. Known accepted run IDs acknowledge retries without another remote start. Ambiguous claims only reconcile: describe the existing run, pin its run ID, read its first history event, and verify workflow type, task queue and the complete original plan through the client's data converter before recording acceptance. Missing history, mismatched content or unavailable Temporal cannot grant a receipt. This prevents an uncertain retry from creating a second run after the original history expires.

This chooses safety over automatic retry availability. A crash after claiming but before sending, or a lost acknowledgement followed by history expiry, leaves the intent pending. Concurrent callers may temporarily see unavailable while the winner is starting. Never clear claims or issue another start RPC automatically. Operator recovery must establish whether the external start occurred before deciding remediation; that administrative recovery workflow is not implemented here. Resubmitting the same start request may verify a now-visible execution, but cannot resend an unverified claim. SDK transport retries of the initial bounded RPC retain Temporal's request identity.

Acknowledging a start means Temporal accepted the execution, not that its business workflow succeeded. Cancellation of the local start coroutine preserves the claim. Temporal RPC/timeout failures become pending/unavailable; plan/route/history mismatches become conflicts. Actual production activity execution, queue capability discovery, activation and identity adapters, transactional release/artifact holds, HTTP routes and recovery administration remain open.

Both start intents and dispatch journals are trusted private application storage containing sensitive metadata/payloads. Preserve them together across restart and disaster recovery. Never prune or independently restore the dispatch journal while replaying old intents. A missing/lost journal cannot safely reconstruct expired remote history. Backup/restore procedures, encryption, retention and production identity/placement guarantees are not established by local tests. The configured target address identifies the destination; operators must not silently repoint it to a different cluster and expect old receipts to imply execution there.

Tests use real SQLite and fake SDK failures by default. Two added local-Temporal integration cases cover async start-service recovery after completion/lost acknowledgement/reopening both journals, and rejection of an existing execution with another plan. Existing restart/replay proof tests continue to run. No change to the interpreter's supported graph semantics is implied.
