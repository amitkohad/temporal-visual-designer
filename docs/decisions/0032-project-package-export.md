# ADR 0032: Portable project export and offline package inspection

Status: accepted for the export/structural-validation increment.

Export an immutable published whole-project release as a versioned ZIP. The package includes the full authored project snapshot (workflows, forms, connection/configuration declarations, layout and optional test definitions) plus each exact published Python source bundle in the release dependency closure. Vendored Python dependencies remain inside their sealed source bundle. Exclude server-owned environment placement/configuration values, tokens, actor metadata, execution payloads and deployment approval evidence by constructing the package only from the published release and scoped catalog exports.

Manifest schema `0.1` carries organization/project/release identity, source revision/time, runtime format `proof.v1`, pinned activity references, a sorted content index and project/executable/package digests. Files are exactly `manifest.json`, `project.json` and `activities/{artifact-hex}.zip`. Index entries bind path, size, media type and SHA-256 of the exact bytes. The package digest hashes canonical manifest JSON excluding its own `package_digest` field. ZIP timestamps, entry order and compression wrapper do not affect logical identity; nested source archive bytes remain part of the indexed identity.

Write deterministic ZIP entries with fixed timestamps and ordinary non-executable file permissions. Inspect entirely in memory without extracting, installing, importing or executing package code. Reject unsupported versions, unsafe/unknown paths, directories, links/special/executable files, encryption, unsupported compression, duplicate paths/JSON keys, excessive nesting, nonfinite JSON, inventory mismatch, checksum mismatch, invalid project structure and conflicting/missing activity identities. Reuse baseline project validation and the existing non-executing activity-bundle validator. Process nested source bundles within an aggregate declared source budget.

Default bounds are 16 MiB archive, 32 MiB outer expanded bytes, 8 MiB per indexed file, 4,000,000 project bytes, 256 KiB manifest, 102 ZIP entries, 100 activity artifacts, 32 MiB aggregate nested source files and 100:1 outer expansion. Hosts can configure operational bounds; fixed manifest collection caps still apply. The HTTP validation route retains the existing 6,000,000-byte body buffer ceiling, so its effective upload limit can be smaller than the codec/export limit.

Export requires fresh scoped `package.export` before storage/catalog lookup. Export only the selected published revision; subsequent draft changes do not alter the package. Read exact artifacts without accepting caller-supplied usage/retention references. This exporter supplies no usage token, so withdrawn artifacts are rejected even if retained elsewhere. Server-owned retained-export orchestration remains future work; this increment does not mutate retention or lifecycle state.

Validation requires fresh scoped `package.import` and matching manifest organization. It returns only the manifest and performs no project, artifact, release, activation or runtime writes. The declared organization and checksums are not signatures or proof of source provenance. Structural validation does not establish target worker capability, executable trust, target configuration readiness or permission to execute. Target import/persistence and activation readiness remain separate gates.

Baseline credential-key and source checks are conservative validation, not general DLP. Authored data/code can contain arbitrary strings; no automatic scrubber can certify every string as nonsecret. This format never queries live secret/configuration providers or exports server-owned evidence/run state. Production provenance/security policy and package signing must be resolved at their own import/deployment gates.
